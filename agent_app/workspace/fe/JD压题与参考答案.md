## 一、前端基础

### Q1. 讲讲事件循环：宏任务、微任务、渲染时机

**考什么**：异步执行顺序的底层机制，5 年经验必问。

**答案**：浏览器里，JS 引擎 + 渲染引擎共用一条主线程，事件循环是"取任务 → 执行 → 检查微任务 → 可能渲染"的循环：

1. 每次从宏任务队列取**一个**任务执行（script、setTimeout、setInterval、I/O、UI 事件）；
2. 一个宏任务执行完后，**清空整个微任务队列**（Promise.then、queueMicrotask、MutationObserver），微任务执行中产生的新微任务也会在本次清空——所以微任务可能"饿死"渲染；
3. 之后浏览器根据是否需要，执行 requestAnimationFrame → 样式计算 → 布局 → 绘制。

Node 的循环是分阶段的（timers → poll → check 等），process.nextTick 优先于微任务；Node 11 后每个阶段之间清空微任务，与浏览器行为基本对齐。

**结合本项目**：渲染进程（浏览器事件循环）和主进程（Node 事件循环）是**两条独立的循环**，靠 IPC 跨进程通信——所以主进程被一个同步阻塞操作卡住（比如 fs 同步读大文件），所有窗口的 IPC 都会延迟响应。这也是为什么 LibreOffice 转换要用 spawn 子进程而不是在主进程内做。

### Q2. 闭包是什么？有什么用？有什么坑？

**考什么**：作用域链 + 内存。

**答案**：闭包 = 函数 + 它定义时所在的作用域。函数执行完，其内部变量本应销毁，但如果内层函数引用着它们且内层函数逃逸（被返回/挂到全局/传给回调），这些变量就跟着函数一起存活。原理是**词法作用域 + 作用域链**：内层函数保存了对创建它的环境的引用。

**用途**：数据私有化（模块模式）、柯里化/偏函数、防抖节流、事件回调携带上下文。

**坑**：① 循环里用 var 声明，回调拿到的全是循环结束后的同一个值（var 是函数作用域，不是每次迭代新绑定）；② 闭包持有大对象引用导致无法回收——内存泄漏的常见来源；③ 闭包里的 this 是运行时绑定的，箭头函数没有自己的 this，恰好从外层词法继承。

### Q3. Promise 的原理和 async/await 的关系

**考什么**：异步编程模型理解深度。

**答案**：Promise 本质是一个**状态机**（pending → fulfilled/rejected，状态单向不可逆）+ 回调队列（then 注册的回调在状态确定后按序执行）。链式调用 then 每次都返回新 Promise，实现回调扁平化和错误冒泡（catch 能接住链上任意一环的 reject）。

async/await 是 Promise + Generator 的语法糖：async 函数内部遇到 await 就"让出"执行权（等效于把后续代码包装成 Promise 的回调）。相比裸 Promise：同步风格的错误处理（try/catch）、顺序依赖代码可读。

**容易讲错的点**：await 后面的表达式立即求值，但函数暂停；多个无依赖 await 应 Promise.all 并发，串行 await 是常见性能浪费。

### Q4. V8 的内存结构与垃圾回收

**考什么**：解释"为什么会内存泄漏"的理论基础。

**答案**：V8 堆分两代：

- **新生代**（小、存活短）：Scavenge 算法，空间换时间——复制存活对象到空闲区，死对象直接丢弃，快；
- **老生代**（大、存活长）：标记-清除（Mark-Sweep）+ 标记-整理（Mark-Compact，清碎片）。标记阶段用三色标记法，配合**增量标记**（分片执行不长时间阻塞）和**并发标记**（后台线程并行）减少停顿。

**GC 的本质是可达性分析**：从根（全局对象、执行栈、DOM）出发引用不到的对象就是垃圾。所以内存泄漏 = "你以为没用了，但它仍可达"——全局变量引用、未移除的监听器、未清理的定时器、闭包持有大对象，都是这个原理。排查方法：DevTools Memory 面板对操作前后取堆快照对比，看哪些对象多了没回收。

### Q5. TypeScript 的类型系统：unknown/any/never，interface vs type

**考什么**：类型功底（JD 明说 TypeScript）。

**答案**：

- **any**：放弃类型检查，会传染——any 参与运算结果还是 any。相当于"关了类型系统"。
- **unknown**：安全的 any。可以接住任何值，但**未经收窄不能使用**（要先 typeof/instanceof/类型守卫），强制你把校验写出来。
- **never**：永远不存在的类型——抛异常函数的返回值、穷尽检查的兜底（switch 里最后一个分支收窄成 never，少写 case 编译器会报错）。

**interface vs type**：interface 支持声明合并（同名的自动合并，适合第三方类型扩展）、只能描述对象；type 支持联合/交叉/映射/条件类型，表达力更强。实践惯例：描述对象形状用 interface，需要组合运算用 type。

**加分**：TS 是"编译期擦除"——类型信息不进入运行时产物（erasure），所以 TS 类型在运行时完全不存在，跨端契约（比如本项目 preload 暴露的 window.electronAPI 类型声明 electron.d.ts）就是靠编译期类型共享，而不是运行时校验。

### Q6. 浏览器渲染管线：从 HTML 到像素，回流与重绘

**考什么**：性能优化的理论根基。

**答案**：渲染主流程：HTML → DOM 树 / CSS → CSSOM 树 → 合并成渲染树（Render Tree）→ 布局（Layout，算几何位置）→ 绘制（Paint，画像素）→ 合成（Composite，分层上屏）。

- **回流（reflow）**：几何属性变化（宽高、位置、内容、字号），触发重新布局，代价最高；
- **重绘（repaint）**：只颜色/阴影变化，不重新布局，中等代价；
- **合成（composite）**：transform、opacity 这类属性不触发回流重绘，只走合成层，代价最低——动画应该用它们。

**优化方向**：批量读（避免读-写交错强制同步布局）、用 class 替代逐条改 style、脱离文档流的动画、will-change 提前建层（滥用反而费内存）。

**结合本项目**：浮窗是透明窗口（渲染成本比普通窗口高）+ 流式文本高频更新，所以浮窗 UI 做得克制、动画用 transform/opacity，内容只渲染最新一段——这是渲染成本意识在产品上的体现。

### Q7. 事件冒泡/捕获与事件委托

**考什么**：DOM 事件机制，高频基础题。

**答案**：DOM 事件传播分三阶段：捕获（从根到目标）→ 目标 → 冒泡（从目标回根）。addEventListener 默认在冒泡阶段触发，第三个参数 true 改为捕获。e.stopPropagation 阻止继续传播，e.preventDefault 阻止默认行为（两者常被混淆）。

**事件委托**：把子元素的监听器挂到父元素上，靠 e.target 判断来源。原理就是冒泡——事件总会经过父节点。好处：动态增删子元素不用反复绑定/解绑、监听器数量从 N 变 1。注意：委托要求事件能冒泡（focus、blur 等不冒泡，需要用 capture 或对应事件）。

## 二、React 技术栈

### Q8. 组件化设计的原则（JD：组件化）

**考什么**：代码组织能力，决定你"资深"与否。

**答案**：三条核心原则：

1. **单一职责**：一个组件只做一件事，拆分依据是"变化原因"——数据和展示分开（容器/展示组件）、可复用逻辑抽 Hook、纯 UI 抽无状态组件；
2. **受控/非受控明确**：状态归属清晰。表单类组件要么全受控（值来自 props），要么明确非受控（内部自管），不能半吊子；
3. **组合优于继承**：children/插槽传递、Render Props、HOC——React 生态的复用方式都是组合，几乎不需要组件继承。

**结合本项目**：screens（页面）/ components（通用 UI 件）/ hooks（useAudioCapture、useKeyboardShortcuts）/ store（纯状态机）/ stream（通信层）/ utils——按层拆分，每层单向依赖。状态机逻辑抽成纯函数 interview-reducer.ts 后，从 React Native 零改动迁移到 Electron——这就是"拆对了"的收益。

### Q9. Hooks 的原理：为什么不能写在条件语句里？

**考什么**：Hooks 机制理解，高频追问。

**答案**：Hooks 的本质是**用调用顺序记住状态**。组件每次渲染，React 按固定顺序执行 Hook 调用，每个 Hook 对应内部链表（fiber.memoizedState）中的一个节点。React 靠"第 N 次调用的 Hook = 链表第 N 个节点"来恢复状态，不靠名字也不靠 key。

所以 Hook 写在条件里，两次渲染的 Hook 数量和顺序不一致，链表错位——状态全部错乱（useState 拿到别人的值）。这是为什么"条件调用 Hook"是硬性规则，ESLint 的 rules-of-hooks 插件就是静态检查这个。

useEffect 的依赖数组同理：React 在提交后对依赖做**浅比较**，变了才执行副作用（清理函数先跑再执行新的）。依赖漏写 → 闭包快照过期的值（stale closure）；依赖写对象/数组字面量 → 每次都变，无限执行。

### Q10. 状态管理怎么选型？为什么你项目用 useReducer？

**考什么**：JD 要求"深入理解状态管理"——重点不是背 Redux 源码，是选型判断力。

**答案**：选型思路：**先看状态形状，再看共享范围，再看团队成本**。

- 组件内短命状态 → useState；
- **多状态互斥联动、转移规则明确（状态机）→ useReducer**：dispatch(action) → 纯函数(旧状态, action) → 新状态。所有转移写在一个纯函数里，可预测、可单测、可日志回放；
- 跨组件共享 → Context（轻）或外部 store（重，Zustand/Redux Toolkit）。判断标准：更新频率——Context 的 value 一变，所有消费者都重渲染，高频更新场景不适合 Context；
- 服务端状态（缓存/重试/失效）→ 交给 React Query 这类库，不要自己再造。

**结合本项目**：面试会话就是天然状态机——采集态/推流态/转写态/回答态互斥转换，所以用 useReducer 收敛全部转移规则。抽成纯函数后（interview-reducer.ts）与 UI 完全解耦：**同一份 reducer 在 RN 和 Electron 两端零改动复用**，这就是状态管理"纯逻辑化"的价值。

### Q11. 虚拟 DOM 是什么？diff 为什么不是 O(n³)？

**考什么**：React 运行机制（JD 明说"主流框架运行机制"）。

**答案**：虚拟 DOM 是 UI 的 JS 对象快照——每次更新先在 JS 里生成新树，与旧树 diff，算出的最小变更再批量应用到真实 DOM（真实 DOM 操作昂贵，JS 对象操作便宜）。

严格的两棵树最小编辑距离是 O(n³)，React 用三个假设把它降到 O(n)：

1. 只比较**同层**节点，不跨层（跨层移动会当成删除重建）；
2. 节点**类型**不同直接整棵替换，不递归比较；
3. **key** 标注同层节点身份，key 稳定时移动/复用，不稳定（用 index）会导致状态错乱和多余重建。

关键认知：虚拟 DOM 的价值不在"比真实 DOM 快"（直接操作有时更快），而在**开发体验 + 批量更新 + 跨端渲染**（同一棵树可以渲染到 DOM/Native/Canvas）。

### Q12. Fiber 架构解决什么问题？

**考什么**：对 React 16+ 核心重构的理解，答得出就区分了背题党和真懂。

**答案**：React 15 的协调是**递归、同步、不可中断**的——组件树大时，一次 diff 可能占用主线程几百毫秒，期间输入/动画全部冻结（掉帧）。

Fiber 把递归改成了**可中断的链表遍历**：

- Fiber 节点 = 组件实例 + 指针（child/sibling/return），遍历不再依赖调用栈，可以随时暂停、保存进度；
- **双缓冲**：current 树（屏幕上）+ workInProgress 树（后台构建），完成后一次切换；
- **优先级调度**：更新按 lane 标记优先级，高优先级（输入）可以打断低优先级（离屏渲染）——时间切片（约 5ms）到点让出主线程；
- 并发能力由此而来：React 18 的 startTransition/useDeferredValue 就是"标记为低优先级、可被打断"。

一句话：**Fiber 让"渲染"从不可分割的原子操作变成了可分片的低优先级任务**。

**结合本项目**：流式翻译场景 llm_chunk 高频逐字更新，如果被问怎么保证 UI 不卡，可以答：把流式文本更新标记为 transition/useDeferredValue（低优先级），用户交互保持即时响应——低优先级更新被拆片执行，逐字到达也来得及渲染。

### Q13. 路由原理与 React Router 7

**考什么**：JD 提到路由。

**答案**：SPA 路由本质是**URL 变化不经过服务器，由 JS 接管**：

- **history 模式**：用 History API（pushState/replaceState）改 URL 且不发请求，监听 popstate 响应前进后退；
- **hash 模式**：改 URL 的 # 部分（不触发请求），监听 hashchange。兼容旧环境，但 URL 丑、不利于 SEO。

React Router 7（Remix 合并后）：数据模式（loader 预取数据、action 处理提交）、嵌套路由、类型安全路由参数。数据加载和路由生命周期绑定，避免"先渲染空壳再 useEffect 拉数据"的水合闪烁。

**结合本项目**：多页面（面试页/历史页/工具页/订阅页）用 react-router-dom 7 组织，配合应用内快捷键 Ctrl+1/2/3 做编程式导航（useNavigate）——快捷键切换页面就是路由跳转，这就是第七节快捷键的实现方式。

### Q14. memo/useMemo/useCallback 的原理和滥用问题

**考什么**：React 性能优化的分寸感。

**答案**：三者的共同机制是**引用相等性**：

- useMemo/useCallback：缓存计算结果/函数引用，依赖不变就返回上次的引用；
- memo：props 浅比较，全相等就跳过重渲染。

**为什么"无效"**：memo 的 props 里只要有一个每次渲染都新建的引用（对象字面量、箭头函数、useMemo 依赖错误），浅比较必然失败，memo 形同虚设还白付比较成本。

**为什么"有害"**：缓存本身有内存和比较成本，对便宜的组件/计算做缓存是负优化。React 官方态度是"性能问题出现后测量再优化"，先缓存是过度设计。

**结合本项目**：状态机用 useReducer 后，dispatch 引用永远稳定——配合 memo 天然有效，不需要 useCallback 包一层。这个组合拳可以主动讲。

## 三、工程化

### Q15. Vite 为什么快？原理是什么？

**考什么**：JD 明点 Vite，高频题。

**答案**：快在三层：

1. **开发期不打包**：基于浏览器原生 ESM。模块请求直接由 dev server 按需返回单个文件，只编译被访问的文件（冷启动和热更新都只处理"正在用的"），而 Webpack 要把整个依赖图打进 bundle；
2. **依赖预构建**：第三方库用 esbuild 预打包（Go 编写、无 JS 中转、并行），缓存到 node_modules/.vite——常见的几百个依赖一次转译，之后秒级命中；
3. **HMR 边界精确**：模块依赖图清晰，文件变更只失效受影响的最小模块链，状态能保留（Webpack 全量失效多）。

生产构建 Vite 底层用 Rollup——**开发快是 ESM 按需，生产稳是 Rollup 成熟生态**。esbuild 单文件转换极快但产物优化能力弱，所以生产不用它打包。

### Q16. Webpack 的原理：loader 和 plugin 的区别

**考什么**：经典工程化题。

**答案**：Webpack 是模块打包器：从入口出发构建**模块依赖图**，经过 loader 转译，再按配置拆 chunk 输出。

- **loader**：单文件转译器。输入源文件，输出可执行模块（ts-loader、babel-loader、css-loader），链式从右到左。本质是"翻译"；
- **plugin**：构建全流程钩子。Webpack 的构建过程（编译、优化、输出）暴露了大量钩子（基于 Tapable 发布订阅），plugin 挂上去在任意阶段做任意事（HtmlWebpackPlugin 生成 HTML、DefinePlugin 注入常量、代码压缩）。本质是"干预构建流程"。

选型一句话：**loader 管"一个文件怎么变成模块"，plugin 管"整个构建流程上还能发生什么"**。本项目渲染层用 Vite（开发体验）、主进程用 tsc 直接编译（Electron 主进程是纯 Node 环境，不需要 bundle 的运行时 polyfill，简单可靠）。

### Q17. pnpm 的原理：为什么快、为什么严格？

**考什么**：JD 明点 pnpm，考包管理器原理。

**答案**：npm/yarn 把每个包的副本拷进每个项目的 node_modules；pnpm 换了两招：

1. **内容寻址存储 + 硬链接**：所有包只存一份在全局 store（按内容哈希寻址），项目的 node_modules 里是**硬链接**——同一磁盘上同一文件多个目录名。安装 = 建链接，秒级、省磁盘；
2. **非扁平 node_modules**：依赖按声明结构排列，通过符号链接暴露给当前包。效果：**未在 package.json 声明的包无法被 import**——npm 下"幽灵依赖"（用了没声明的包却恰好能用）在 pnpm 下直接报错，倒逼依赖声明规范。

**结合本项目**：pnpm workspace 管理 fe/be/shared 多包；原生模块目录（electron/audio/native）把 install 脚本改成 no-op——杜绝 pnpm 安装时隐式触发 node-gyp 裸编译（Electron ABI 下裸编译产物是坏的），编译统一走 ensure-native 自动化脚本。这是 pnpm 生态踩坑的实战案例。

### Q18. monorepo 怎么治理？你项目怎么做的？

**考什么**：大型项目工程治理经验（JD 原话）。

**答案**：治理要点：**目录边界 = 依赖方向**（共享层不能反向依赖业务层）、统一脚本入口、锁文件唯一、版本一致性、CI 按变更目录精准触发。

**结合本项目**：workspace 分 fe（前端/桌面）、be（后端）、shared（跨端共享逻辑）——三端协议（wire protocol 编解码、PCM 归一化算法）的规格和测试用例放 shared，任何一端改协议，三端跑同一套字节级测试。协作成本从"三端口头对齐"变成"测试说了算"。

### Q19. ESLint 9 和 typescript-eslint 的工程实践

**考什么**：代码质量工程。

**答案**：ESLint 9 用 **flat config**（eslint.config.js），取代了老 eslintrc 的级联配置——配置合并规则更直白，TS/JS 混用项目一条配置搞定。typescript-eslint 提供两类规则：语法级（快）和**类型感知**（需要 project 信息，能查出 await 误用、类型不安全的 any 传递等，但慢——日常开发跑轻量集，CI 跑全量）。

分工：ESLint 管**正确性**（规则）和风格的一部分，Prettier 管**格式化**（冲突通过 eslint-config-prettier 关闭格式类规则）。团队底线是"CI 不过不能合"。

**结合本项目**：ESLint 9 + typescript-eslint 8，同时 lint src/（渲染层）和 electron/（主进程）两份代码；配合 typecheck 脚本（两个 tsconfig 各跑一次）和 vitest，形成提交前的三道闸。

### Q20. TypeScript 工程治理：你项目的类型边界怎么设计？

**考什么**：接口抽象能力在工程上的落地。

**答案**：类型治理的关键是**在边界处定义契约**，而不是全项目一把梭：

1. 严格模式全开（strict），新代码禁止 any（用 unknown + 收窄）；
2. **多 tsconfig 分层**：不同运行环境不同编译目标。本项目渲染层走 Vite（浏览器目标），主进程单独 electron/tsconfig.json 编译成 CJS 产物（package.json main 指向 dist-electron/main.js）——同一门语言，两个编译目标；
3. **跨进程契约 = 类型声明文件**：preload 暴露的 window.electronAPI 用一份 electron.d.ts 声明（四个分类、每个方法的入参出参），渲染进程写代码全靠这份类型提示——**preload 的 API 就是渲染进程的 SDK**。改 API 时类型报错会一路红到所有调用点，契约变更零遗漏。这就是"接口抽象"在 TS 项目里最务实的形式。

### Q21. 环境与构建链治理：讲一个你踩过的坑和固化方案

**考什么**：工程化能力最真实的体现——把坑变成流程。

**答案**（结合本项目，三个真实案例，讲一个即可，三个都有是加分）：

1. **Electron 43 二进制下载坑**：Electron 43 起安装包把二进制改为懒下载，且下载用的 Node fetch 不读系统代理——内网/国内环境 pnpm install 直接卡死。排查链路：装不上 → 看下载日志 → 确认网络层 → 换镜像。固化方案：配置 ELECTRON_MIRROR（npmmirror 镜像）或 NODE_USE_ENV_PROXY，写进环境文档和 CI 配置；
2. **dev 首次启动竞态**：开发模式 electron 入口要等 tsc 产出 main.js，vite 和 tsc 并行启动时 electron 可能先于产物就绪而启动失败。固化方案：launch-electron 脚本显式等待 tsc 产物再拉起；
3. **原生插件编译自动化**：C++ addon 必须按 Electron ABI 编译，手工会漏。固化方案：ensure-native 脚本在 dev 启动前和打包前自动检查/编译，native 目录的 install 钩子改成 no-op 防隐式编译。

**归纳一句（面试金句）**：工程化的价值就是"把踩过的坑固化进脚本，让新机器、新同事零成本继承"。

### Q22. Git 协作流程与 commit 规范

**考什么**：协作基本功。

**答案**：分支模型（主干开发/feature 分支 + PR）、commit 语义化（type: feat/fix/refactor/docs，scope 标注模块）、PR 描述"为什么改"而不只是"改了什么"、review 关注点（接口契约变更、错误路径、性能敏感点、测试覆盖）。

**结合本项目**：提交历史本身就是规范示例——fix(electron): / feat(electron): 前缀 + 一句说清问题（"TSFN 退出竞态修复""后端地址统一云端"），每个 commit 可独立回溯。面试时可以说：commit message 就是变更日志，半年后排查问题靠的就是它们。

## 四、浏览器机制 / 网络 / 性能

### Q23. HTTP/1.1 → HTTP/2 → HTTP/3 各自解决什么问题？

**考什么**：网络协议演进，JD 要求"熟悉网络协议"。

**答案**：

- **1.1**：一个连接上请求串行（队头阻塞），所以浏览器开 6 个并行连接补偿；每个请求带完整文本头。
- **2**：单连接**多路复用**（帧 + 流编号，多个请求/响应交错传输，互不阻塞）+ 头部压缩（HPACK 索引表）+ 服务器推送。但**TCP 层的队头阻塞仍在**——一个包丢了，后面的流都得等重传（TCP 保证有序）。
- **3**：换 **UDP + QUIC**。可靠性和拥塞控制从 TCP 移到 QUIC 层，单个流的丢包不再阻塞其他流（真正的无队头阻塞）；连接建立 0-RTT（缓存了密钥直接发数据）；连接迁移（换 IP/网络不断连）。

面试回答线：**1.1 解决"能不能并发"，2 解决"应用层并发"，3 解决"传输层阻塞"**。

### Q24. HTTPS 握手做了什么？（TLS 1.3）

**考什么**：安全通信原理。

**答案**：目标：在不安全的信道上协商出**只有双方知道的会话密钥**，并验证服务器身份。

TLS 1.2 两次往返；TLS 1.3 简化成 1-RTT：客户端 hello 直接带密钥协商参数（ECDHE）→ 服务器回证书 + 协商参数 → 双方各自算出相同会话密钥，开始加密通信。要点：

- **非对称加密只用于握手**（传证书、协商密钥），业务数据用对称加密（快）；
- **证书 = 服务器公钥 + 身份信息 + CA 签名**，链式验证到根证书（浏览器内置）；
- 前向保密：会话密钥是临时协商的（ECDHE 的 E），私钥泄露不影响历史流量解密。

### Q25. WebSocket 的原理：为什么适合你项目的音频推流？

**考什么**：协议选型 + 本项目理解。

**答案**：WebSocket 是 TCP 上的**全双工长连接**：HTTP 请求带 Upgrade 头完成握手（101 状态码），之后协议切换到帧模式——双方随时互发，单帧头仅 2 字节起，无 HTTP 头开销。

对比：

- **HTTP 轮询**：每 40ms 一个新请求，每个请求带几百字节头 + 三次握手成本（长连接可省握手但头还在），浪费且延迟抖动；
- **SSE**：单向（服务器→客户端），不能推音频；
- **WebRTC DataChannel**：P2P 低延迟，但要 ICE 打洞、SFU 等设施，对"客户端→服务器"单向上行是杀鸡用牛刀。

**结合本项目**：40ms 一帧、每秒 25 帧的持续小包上行——正是 WebSocket 最典型场景。配合二进制帧（省 40% 带宽）、指数退避重连、generation 防竞态、client_hello 握手确认后才开流。wss（WS over TLS）保证音频内容加密传输。

### Q26. 强缓存与协商缓存

**考什么**：缓存机制，前端基础高频。

**答案**：

- **强缓存**（不发请求）：Cache-Control: max-age=N（HTTP/1.1 标准，immutable 可加）或 Expires（1.0 遗留）。未过期直接本地取，状态码显示 200 (from disk cache)；
- **协商缓存**（发请求问一下）：ETag/If-None-Match（内容指纹，精确）或 Last-Modified/If-Modified-Since（时间，秒级精度有缺陷）。没变回 **304**，不传 body。

**工程实践**：文件名带内容哈希的静态资源（Vite 产物 asset-xxxx.js）+ max-age 一年 + immutable（强缓存拉满）；index.html 短缓存或 no-cache（入口必须走协商，保证发版即更新）。原理一句话：**内容可寻址的资源用强缓存，入口文件用协商缓存**。

### Q27. CORS 的原理与预检

**考什么**：跨域机制。

**答案**：同源策略（协议+域名+端口一致）限制跨源读取，但**请求本身能发出去**——浏览器拦截的是响应。CORS 是服务器声明"我允许哪些源访问"的机制：响应头 Access-Control-Allow-Origin。

**预检（preflight）**：非简单请求（PUT/DELETE、自定义头、Content-Type 非表单）先发一个 OPTIONS 探路，服务器回允许的方法/头清单，浏览器确认后才发正式请求。预检是浏览器代理执行的，不是 JS 代码发的。

**结合本项目**：桌面端用 wss 连云端后端（后端地址统一云端管理），属于浏览器跨源场景；面试可补充：Electron 里如果页面是 file:// 或自定义协议加载，跨域规则不同（file:// 源为空，一般建议生产用自定义协议 protocol.handle 加载本地页面，这也是安全最佳实践之一）。

### Q28. XSS 与 CSRF 的原理和防御（含 Electron 场景）

**考什么**：Web 安全基础 + Electron 安全延伸。

**答案**：

- **XSS**：恶意脚本被注入页面执行。反射型（URL 参数直接回显）、存储型（入库后展示）、DOM 型。防御：输出编码、输入校验、**CSP**（Content-Security-Policy 白名单限制脚本来源）、少用 dangerouslySetInnerHTML；
- **CSRF**：利用浏览器自动携带 Cookie 的特性，诱导用户在已登录站点上执行非本意请求。防御：SameSite Cookie、CSRF Token、验证 Referer/Origin。

**Electron 场景的延伸**（和第五节安全边界呼应）：渲染进程被 XSS 打穿后，能造成多大损失取决于架构——nodeIntegration 开着 = 攻击者直接拿到本机权限（RCE）；contextIsolation + contextBridge 白名单 = 攻击者最多调用那几十个受限方法。所以 Electron 安全的第一道防线不是防 XSS 本身，而是**假设渲染进程会被攻破**去设计权限边界。CSP 同样要配（script-src 'self'），防止远程脚本注入。

### Q29. 前端性能优化全景：你做过哪些优化？

**考什么**：JD 原话"常见前端性能优化方法"。

**答案**（按三段式答，结合本项目实例）：

1. **加载**：包体积（tree-shaking、懒加载路由）、压缩、CDN、缓存策略（Q26）、资源预加载。Electron 特有：应用冷启动——主进程 app.ready 前只做必须初始化、preload 精简（它同步阻塞首屏）、原生插件编译前置到安装期；
2. **渲染**：减少回流重绘（Q6）、动画走合成层、长列表虚拟化、长任务切分。本项目：浮窗透明窗口渲染成本高 → UI 克制 + 动画只用 transform/opacity；
3. **运行时/网络**：数据量压到最小（本项目归一化把音频数据砍到 1/12）、协议紧凑（二进制 Wire Protocol 省 40% 带宽）、静音帧过滤（无声时整条链路空闲，省 CPU）、事件循环不被阻塞（重活放子进程）。

**方法论**：**先测量再优化**——Performance 面板、Lighthouse、app.getAppMetrics()，用数据定位瓶颈，别凭感觉优化。

## 五、Electron 架构（JD 核心硬性要求）

### Q30. Electron 主进程/渲染进程/preload 的职责划分，你的项目怎么分？

**考什么**：JD 硬性第 2 条，Electron 面试第一问。

**答案**：原理：

- **主进程**（唯一）：Node.js 环境。创建窗口、应用生命周期、系统能力（托盘/快捷键/文件/原生插件）。**所有系统资源和共享状态的所有者**；
- **渲染进程**（每窗口一个）：Chromium 环境。UI 渲染和交互，默认与浏览器页面同等受限；
- **preload**：每窗口加载前执行的桥，唯一同时接触 Electron 能力与 DOM 的位置，负责把主进程能力白名单化摆渡给页面。

关键认知：**主进程不是渲染进程的父进程，它们是平级 OS 进程，只靠 IPC 通信**。

**结合本项目**的划分：

| 职责 | 位置 | 内容 |
|---|---|---|
| 系统音频采集 | 主进程 | WASAPI C++ 插件 + 采集循环 |
| WebSocket 推流 | 主进程 | StreamClient（ws 库）+ 重连 |
| 文件转换/下载 | 主进程 | LibreOffice spawn、下载器 |
| 托盘/窗口管理 | 主进程 | Tray、主窗+浮窗 |
| UI/交互 | 渲染进程 | React 应用（主窗、浮窗各一份） |
| 麦克风采集 | 渲染进程 | Web Audio（getUserMedia 是浏览器 API）→ 帧走 IPC 给主进程 |
| 能力暴露 | preload | audio/fileConvert/window/storage 四分类 |

### Q31. 为什么把音频采集和推流放在主进程？（架构决策）

**考什么**：JD 第 6 条"能清晰说明架构决策"。

**答案**：三个理由：

1. **能力依赖**：WASAPI 原生插件只有 Node 环境能加载（require .node），系统音频采集天然是主进程能力；
2. **生命周期解耦**：采集/推流的生命周期应该跟"应用"而不是"窗口"绑定——用户最小化到托盘、关闭主窗口，采集都不该中断（辅助工具的核心体验是后台常驻）；
3. **单点持有连接**：会话状态（sessionId、音轨列表、重连逻辑）由主进程一个 StreamClient 持有，主窗和浮窗都只是订阅者——否则每个窗口各自建连，会话管理会爆炸。

同时有一个诚实的边界：**麦克风采集留在渲染进程**——getUserMedia 是浏览器 API，渲染进程天然能拿，采集到的帧经 IPC 交给主进程统一推流。设计上"各在擅长的位置做擅长的事"，主进程做系统能力和网络单点，渲染进程贡献浏览器能力。

### Q32. IPC 的两种模式怎么选型？数据怎么传？

**考什么**：JD 硬性第 3 条"进程间通信"。

**答案**：两种模式：

- **请求-响应**：`ipcRenderer.invoke` → `ipcMain.handle` → 返回 Promise。一问一答（读文件、查状态、执行转换）；
- **单向推送**：主进程 `webContents.send` → 渲染进程 `ipcRenderer.on`。主进程主动广播（转写结果、LLM 流、下载进度）。

**底层事实**：消息经 Chromium 的消息管线在本机进程间传递，**载荷经过结构化克隆（序列化拷贝）**——不是传引用。所以两个工程结论：① 高频大对象 IPC 有拷贝成本，要控制消息频率和体积；② 二进制（Buffer/TypedArray）有高效传递通道，本项目的麦克风 PCM 帧走 `ipcRenderer.send`（单向、无回执、不等响应）而非 invoke——避免每次 40ms 一次往返握手。

**性能进阶**（被追问时讲）：Electron 支持 **MessagePorts**——像浏览器 MessageChannel 一样，主进程和渲染进程各持端口直连，绕过常规 IPC 通道，适合高频二进制流的点对点传输。

### Q33. Electron 安全边界：nodeIntegration / contextIsolation / sandbox

**考什么**：JD 硬性第 2 条"安全边界"，必考。

**答案**：三个开关的**版本演变**（答出数字说明真懂）：

- **nodeIntegration**：渲染进程能否直接用 Node。Electron 1 默认 true（灾难性默认值，Signal Desktop 等应用因此被打穿过），**Electron 5 起默认 false**；
- **contextIsolation**：preload 与页面的 JS 上下文是否隔离。**Electron 12 起默认 true**——隔离后页面拿不到 preload 内部的 require/变量，只能拿到 contextBridge 显式暴露的白名单；
- **sandbox**：渲染进程跑在 Chromium 沙箱内，能触达的系统资源被最小化（沙箱内 preload 只能 import 有限模块）。**Electron 20 起默认开启**。

攻击链理解：**渲染进程被攻破（XSS/供应链投毒）→ nodeIntegration 开着 = 直接 RCE；contextIsolation 关着 = 攻击者摸到 preload 的 require = RCE；全开默认 = 攻击者最多调用 contextBridge 暴露的受限方法**。所以安全基线是"默认值别关 + preload 只暴露最小必要能力 + 绝不把 ipcRenderer 整个暴露给页面"。

**结合本项目**：三个开关全默认 + contextBridge 暴露四分类白名单 API（每个方法职责单一、入参在主进程校验）——攻击者拿到渲染进程也只能"开始采集、查个状态"，文件路径、任意命令都不可达。

### Q34. 为什么不能用 nodeIntegration？（把攻击链讲透）

**考什么**：对安全原理的真实理解，不是背结论。

**答案**：渲染进程里跑的代码**不全是你的代码**——三方 npm 依赖（供应链投毒）、远程内容、XSS 注入都可能进页面执行。nodeIntegration=true 时，页面 JS 的 require 直接就是 Node 的 require：

```
XSS 注入一行 <img onerror="require('child_process').exec('...')">
```

一个反射型 XSS 就直接变成**远程代码执行**（RCE），且权限是当前用户完整权限（读文件、装后门、勒索）。历史上 Signal Desktop 的 CVE-2018-1000006、Discord 的 RCE 事故都是这条链。

结论：**渲染进程里的代码一律视为不可信**（untrusted），Node 能力只锁在主进程，经 preload 白名单 + IPC 按需申请。这也是 Electron 官方把默认值一路收紧到今天的原因（Q33 的版本线）。

### Q35. preload 怎么设计才是好的？

**考什么**：API 设计能力在安全上的体现。

**答案**：原则：

1. **最小暴露**：只暴露页面真正需要的操作，一个方法一件事（startCapture 而不是通用 exec）；
2. **不透传**：绝不 `window.ipcRenderer = ipcRenderer`（页面就能伪造任意消息），也绝不暴露"执行任意命令/读任意路径"这类未校验能力——那等于绕过 nodeIntegration 的禁用重新造了个 RCE 后门；
3. **入参校验在主进程**：渲染进程的入参不可信，ipcMain.handle 里校验参数、校验 event.senderFrame 来源（只接受自己窗口的请求）；
4. **订阅可清理**：每个 onXxx 返回取消订阅函数，组件卸载时调用——防止重复订阅和内存泄漏。

**结合本项目**：preload 按**职责域**分四类（audio / fileConvert / window / storage），通道命名 `域:动词`（audio:start-capture、file:convert、window:toggle-overlay、storage:get），渲染进程的 window.electronAPI 类型声明即契约。加新能力（如截图）就在对应域扩展，不破坏结构。

### Q36. 多窗口管理：主窗口 + 浮窗怎么设计？

**考什么**：JD 硬性第 3 条"多窗口管理"。

**答案**：要点：

- **窗口 = 独立渲染进程**：内存与状态完全隔离，通信必须走主进程中转（渲染进程之间不能直接通信——或者说没有直接的机制，必须主进程转发）；
- **主进程统一持有窗口引用**：一个窗口管理器负责创建/销毁/状态查询，窗口销毁后引用置空、send 前判活（webContents.send 到已销毁窗口会抛异常导致主进程崩溃）；
- **数据分发（fan-out）**：主进程事件一次产生，各窗口各发一份——AudioCaptureManager emit 一次，主窗和浮窗各收各的。加第三个窗口只是多一个 send，零侵入；
- **全局状态单一管理**：ContentProtection 这类全局状态在主进程用布尔变量统一持有，切换时遍历 BrowserWindow.getAllWindows() 同步设置——新建窗口不自动继承，创建后补设一次。

**结合本项目**：浮窗 = 独立 BrowserWindow（transparent + frame:false + alwaysOnTop + skipTaskbar + 鼠标穿透 + 全工作区可见），只做"最新翻译结果展示"一件事；主窗是完整会话界面。职责不同、进程隔离、数据同源。

### Q37. 应用生命周期：启动、单实例、退出清理

**考什么**：JD 硬性第 3 条"应用生命周期"。

**答案**：

- **启动**：app.whenReady() 之后才创建窗口（ready 前拿不到窗口 API）；macOS 惯例 activate 事件里重建窗口（点 Dock 图标恢复）；
- **单实例锁**：requestSingleInstanceLock()——拿不到锁说明已有实例在跑，直接退出并让旧实例唤起窗口（second-instance 事件）。桌面工具类应用必做，否则用户点两次图标开两个应用、两个实例抢同一份本地数据；
- **window-all-closed 平台差异**：Windows/Linux 惯例全部窗口关闭即退出（app.quit），macOS 惯例留着应用（窗口重开由 activate 处理）。**托盘常驻应用**则是另一条路：关主窗 = 隐藏，应用随托盘生命周期；
- **退出清理**：before-quit 里按序停采集、断开网络、释放原生资源——顺序错了就是崩溃。

**结合本项目（真实 bug 案例，强烈建议讲）**：WASAPI 采集线程在无音频播放时阻塞在 GetNextPacketSize 上，直接释放 TSFN（线程安全函数）会与仍活跃的采集线程竞态——**必须在退出时先发 Stop 唤醒采集线程，join 等它结束，再释放 TSFN**。这就是提交记录里"TSFN 退出竞态修复"的完整故事：原生模块的生命周期必须遵守"先停流 → 等线程 → 再释放"的顺序。

### Q38. 本地存储怎么做？为什么不用 localStorage？

**考什么**：JD 硬性第 3 条"本地存储"。

**答案**：Electron 里三档方案：

- **渲染进程 localStorage**：最简单但不可控——受浏览器存储策略影响（配额、清理时机），只对单窗口可见，主进程读不到；
- **主进程 JSON 文件**：完全可控、跨窗口共享、可迁移可备份，适合配置/小数据。electron-store 这类库是它的封装（原子写、schema 校验）；
- **SQLite**（better-sqlite3 等）：结构化大数据（聊天记录、历史会话），支持索引查询。

**选型判断**：结构化查询需求决定要不要上 SQLite；配置类数据 JSON 文件足够。

**结合本项目**：storage 走 IPC → 主进程文件系统（preload 的 storage 分类：get/set/remove）——主进程侧的托盘/窗口逻辑和渲染进程读同一份配置，数据源唯一。下载器的断点续传进度也落本地 JSON（URL、总大小、已下载字节数、临时文件路径），恢复时读文件 + Range 续传 + 大小校验（4KB 容差防块对齐误判）。这就是"用文件做状态持久化"的实战。

### Q39. 原生模块：node-gyp / N-API / node-addon-api 是什么关系？

**考什么**：JD 硬性第 1 条 + 简历有 C++ 插件，必然深挖。

**答案**：

- **node-gyp**：编译工具。读 binding.gyp 配置（源文件/头文件/系统库），调用本机编译器（Windows 上 MSVC）把 C++ 编成 .node（本质是改了扩展名的 DLL）；
- **N-API**：Node 官方定义的 **C 层 API 规范**，ABI 稳定——插件跨 Node 大版本不用重新编译。它的关键能力之一就是 ThreadSafeFunction：把"任意线程调用 JS 回调"变成线程安全队列（JS 只能跑在 v8 线程，C++ 线程直接调是未定义行为）；
- **node-addon-api**：N-API 之上的官方 **C++ 封装库**（Napi:: 命名空间），提供类封装和生命周期管理。**项目实际用它，它底层就是 N-API**；
- **electron-rebuild / electron-builder 重编译**：Electron 内置 Node 的 ABI 与系统 Node 不同，插件必须针对 Electron 编译——这是 Electron 原生模块特有的坑。

**结合本项目**：wasapi_loopback.cc 用 node-addon-api 的 Napi::ThreadSafeFunction（NonBlocking 模式：塞任务不阻塞采集线程，队列满 64 帧丢新帧——实时音频"宁可丢不能停"）。编译由 ensure-native 脚本全自动完成，dev 和打包前自动保证插件就绪。

### Q40. 自动更新怎么设计？（本项目未做，讲方案）

**考什么**：JD 硬性第 4 条"打包、签名、发布及升级流程"。

**答案**：先说结论：**"本项目目前未接入自动更新，但方案我清楚"**——诚实 + 完整方案是加分。

**原理**：构建时生成**发布元数据**（latest.yml：版本号、安装包 URL、sha512 校验和）→ 上传到发布服务器（GitHub Releases/S3/通用 HTTP）→ 应用启动后 checkForUpdates 拉元数据比对版本 → 有新版本下载安装包 → **校验 sha512 + 验证代码签名** → 应用退出时由独立进程执行安装器（或下次启动时安装）。

**两个更新通道**：

- **electron-updater（electron-builder 生态）**：功能最全（支持 Linux、Windows 上校验签名、差分更新、灰度发布 stagingPercentage）。注意：**Windows 上只支持 NSIS 安装包**，不支持 Squirrel.Windows；
- **Electron 内置 autoUpdater**：Windows 上走 Squirrel.Windows（本项目打包用的就是 squirrel-windows），macOS 走 Squirrel.Mac（原子替换 app bundle，要求 zip 产物 + 代码签名）。

**macOS 发布链**：Developer ID 签名 → 公证（notarization，Apple 审核后凭证票据，Gatekeeper 放行）→ zip/dmg 产物。未签名未公证的应用在别人的 Mac 上直接被拦。

**结合本项目**：打包用 electron-builder + Squirrel.Windows。若接自动更新：Windows 要么用内置 autoUpdater（匹配现有 Squirrel 安装器），要么迁移 NSIS + electron-updater 拿差分更新和灰度；发布走云端存储（后端地址已统一云端，发布物同理）。

### Q41. 断线重连与异常恢复怎么设计？

**考什么**：JD 硬性第 3 条"异常恢复"，本项目有完整实现。

**答案**（结合本项目，四个机制讲清）：

1. **断线检测**：onclose 看关闭码——1000 正常关闭（用户主动停），非 1000 视为异常断开。主动断开时把重试计数置最大值再 close(1000)，双重保险防误触发重连；
2. **指数退避重连**：500ms×2ⁿ、上限 30s、最多 10 次，总窗口约 2.5 分钟。**为什么指数退避**：服务端过载时固定间隔会让所有客户端同步蜂拥重连（雪崩），间隔递增给服务端恢复时间。**为什么有限次**：真断网（飞行模式）无限重试只烧电，10 次覆盖 WiFi 切换/电梯/隧道等瞬时断网，用尽后进 dead 状态让用户手动重试；
3. **generation 防竞态**：每次建连递增 generation，所有异步回调（onopen/onmessage/onclose/onerror）入口处校验快照——旧连接的延迟回调（网络栈缓冲）到达时发现 generation 已变，直接丢弃。四个事件是全部异步入口，入口拦截即全拦截；
4. **会话恢复**：重连不是从零开始——sessionId 和活跃音轨列表还在内存，重连成功后重建会话上下文（session_start + track_start），后端恢复 ASR 上下文和对话历史，用户无感。

另外的降级路径：WASAPI addon 加载失败 try-catch 兜底，降级为纯麦克风（Web Audio）模式——**核心功能可用性不依赖单一模块**。系统音频和麦克风是两条独立采集路径，一条挂了不影响另一条。

### Q42. 进程崩溃怎么处理？

**考什么**：JD 硬性第 3 条"异常恢复"+"进程崩溃"（第 5 条）。

**答案**：分层应对：

1. **预防**：已知崩溃点工程化规避——本项目两个真实例子：send 到已销毁 webContents 会崩 → send 前统一判活封装；TSFN 与采集线程竞态 → 退出顺序治理（Q37）；
2. **捕获与降级**：渲染进程 render-process-gone / unresponsive 事件 → 记录现场（crashReason）→ 重建窗口恢复现场；主进程 process.on('uncaughtException') 记日志（注意：主进程未知异常不能盲目 continue，状态可能已坏，通常记日志后优雅退出重启）；子进程（LibreOffice）崩溃 → 超时杀树兜底（Q43）；
3. **上报与定位**：crashReporter 把崩溃转储（minidump）上传到收集服务（Sentry Electron 等），线上问题靠崩溃堆栈定位；
4. **自愈**：崩溃后 relaunch 策略（app.relaunch + exit），防止用户卡在"死了的壳"里。

**结合本项目**：WASAPI 采集循环里每类错误都有明确错误码（E_WASAPI 不可恢复 / E_PCM 可恢复重试）——**错误分类决定恢复策略**：可恢复的重试，不可恢复的停止采集并明确提示用户，绝不静默失败。

### Q43. 外部进程管理：spawn 子进程的坑

**考什么**：主进程工程能力（本项目 LibreOffice 真实案例）。

**答案**（结合本项目）：

- **超时治理**：spawn 自带的 timeout 只杀父进程——LibreOffice 会 fork 子进程，只杀主进程会留下孤儿进程。项目手动管理超时：Windows 上 taskkill /F /T（强制 + 整棵进程树），Unix 上 SIGKILL 兜底。5 分钟硬超时（大文件转换需要时间）；
- **编码坑**：Windows 命令行参数 GBK 代码页与程序内部 UTF-8 不一致，中文路径会乱码找不到文件。解法不是修编码，而是**绕开编码**：文件名含非 ASCII 时先复制到全 ASCII 的临时目录转换，完了搬回改名；
- **环境隔离**：spawn 时传干净的 env + cwd 指定程序目录 + windowsHide 防黑窗闪烁；
- **幂等自检**：LibreOffice 版本自检只跑首次并缓存结果，避免每次转换都 spawn 一遍。

### Q44. UtilityProcess 是什么？什么时候用？

**考什么**：新版本 Electron 认知（Electron 22+）。

**答案**：UtilityProcess 是 Electron 官方提供的**独立 Node 子进程**（对应 Chromium 的 utility process）：Node 环境、与渲染进程隔离、可用 MessagePorts 高效通信，崩溃不影响主进程。

**选型**：

- 重 CPU 活（编码、加密、大 JSON 解析）→ worker_threads 同进程内线程就够，但**写坏会拖垮主进程**；UtilityProcess 崩溃可控可重启；
- 不受信任的代码（插件系统、用户脚本）→ 必须独立进程跑（沙箱），UtilityProcess 是官方答案；
- child_process（本项目 LibreOffice 用法）→ 外部已有程序，不用 Node 环境。

一句话：**UtilityProcess = "Node 环境 + 进程隔离 + 可重启"**，填补 worker_threads 和 child_process 之间的空档。

### Q45. Electron vs Tauri 怎么选？

**考什么**：技术选型判断力。

**答案**：

| 维度 | Electron | Tauri |
|---|---|---|
| 体积 | 80MB+（自带 Chromium） | 10MB 级（用系统 WebView） |
| 一致性 | 各平台 Chromium 行为一致 | 各平台 WebView（Edge/WebKit）有差异 |
| 后端语言 | Node.js | Rust |
| 生态/成熟度 | 极成熟（VS Code/Slack） | 成长中 |
| 原生扩展 | node-gyp/N-API，成熟 | Rust 侧直接写 |

**结论**：团队栈是 Node/TS、需要成熟的 C++ 原生插件路径（node-addon-api）、追求各平台渲染行为一致 → Electron。Tauri 适合对体积敏感、团队有 Rust 能力的场景。**选型不是比谁先进，是比谁的约束和团队匹配**——承认 Tauri 的体积优势再说明取舍，比贬低对手高级。

## 六、Electron 性能与问题定位（JD 硬性第 5 条）

> 面试官爱问"如果 X 慢了/崩了你怎么查"。通用答题框架：**先定位（工具+数据）→ 分进程归因（主/渲染/GPU）→ 对症优化 → 验证**。

### Q46. 启动慢怎么定位和优化？

**考什么**：JD 第 5 条"定位启动慢"。

**答案**：

**定位**：把启动分三段计时——主进程 ready 前（初始化逻辑）、窗口创建到白屏（preload + 页面加载）、白屏到可交互（首屏渲染）。用 trace（Content Tracing / chrome://tracing）看每段耗时。

**常见原因与优化**：

- **app.ready 前干了太多事**：数据库初始化、大配置加载、模块同步 require——移到 ready 后或懒加载，非关键初始化用 idle 时机；
- **preload 拖慢首屏**：preload 同步执行且阻塞渲染，里面 require 一堆重 npm 包会直接拖慢窗口出现——preload 只做桥，重逻辑放主进程；
- **后台节流坑**：Electron 默认 backgroundThrottling 会节流后台窗口的定时器/渲染，某些场景下首屏被卡住（社区有案例首屏 4.2s → 1.1s，节流占一半优化空间）——必要时 webPreferences 关闭并加 Chromium 开关兜底；
- **打包产物**：asar 里文件多/大影响读取，files 白名单瘦身。

**结合本项目**：启动路径的治理都在**工程侧**——原生插件编译前置（ensure-native 在 dev/打包前完成，启动时直接加载不编译）、Electron 二进制下载镜像固化（安装期不卡）、dev 启动竞态修复（不空等）。可以讲：启动性能 = 运行时优化 + 构建链优化，两半都要。

### Q47. 内存泄漏怎么排查？

**考什么**：JD 第 5 条"内存泄漏"。

**答案**：

**定位**：`app.getAppMetrics()` 按进程看 workingSetSize 和 CPU（注意过滤出 Browser/Renderer/Utility，GPU 等辅助进程内存画像不同）；`process.memoryUsage()` 看 heapUsed/rss——**RSS 涨但堆不涨 → 怀疑原生层/外部缓冲，堆涨 → 查 JS 引用**。操作前后各取堆快照对比（主进程 v8.writeHeapSnapshot，渲染进程 DevTools Memory），看什么对象只增不减。

**Electron 高频泄漏源**：

1. **IPC 监听器不清理**：每次挂载都 ipcRenderer.on，卸载不移除——回调被重复注册，泄漏监听器和闭包。对策：onXxx 返回取消订阅函数（本项目 preload 就是这么设计的），组件卸载时调用；可用 listenerCount 验证；
2. **BrowserWindow 引用不释放**：窗口关了但主进程还持有引用，整个渲染进程的内存都不回收。对策：closed 事件置空引用、统一窗口管理器管理；
3. **子进程/定时器/全局缓存**：spawn 的子进程不回收、setInterval 不清、无上限的内存缓存；
4. **渲染进程大对象全局持有**：window.xxx = 大数组，永远可达。

**结合本项目**：preload 每个 onXxx 返回 removeListener 封装 + 窗口 send 前判活 + 下载临时文件清理（cleanupDownload）——防泄漏是 API 设计时就考虑好的，不是出问题再修。

### Q48. CPU 占用高怎么查？

**考什么**：JD 第 5 条"CPU 占用高"。

**答案**：

**定位**：先分进程——任务管理器看是主进程还是某个渲染进程；DevTools Performance 面板（渲染进程）看 JS 函数耗时，主进程用 --inspect 挂 CPU profiler。

**主进程常见元凶**：

- 同步阻塞操作：fs 同步 API、CPU 密集计算（加密/解析）——异步化或搬 worker/子进程；
- **IPC 洪水**：渲染进程高频小消息（比如每个状态变化都发一条）——批处理合并；
- GC 压力：内存泄漏导致频繁 GC。

**渲染进程常见元凶**：高频 setState、无节流的滚动/输入处理、无限循环动画。

**结合本项目（真实优化案例）**：WASAPI 采集用 10ms 轮询，**没有音频播放时 Windows 仍持续吐包**（内容全 0）——检查 AUDCLNT_BUFFERFLAGS_SILENT 标志位，静音帧直接丢弃，不归一化、不编码、不发送。**无声时整条采集链路空闲**，这省掉的是持续性的 CPU。这个故事把"CPU 高怎么查"（轮询开销 → 数据流各环节观察 → 找到无意义的工作）和"怎么优化"（源头过滤）完整讲出来了。

### Q49. 页面卡顿/掉帧怎么定位？

**考什么**：JD 第 5 条"页面卡顿"。

**答案**：

**定位**：Performance 面板录一段交互——看主线程长任务（long task > 50ms）、帧率（FPS 掉帧段）、强制同步布局（读-写交错）。渲染进程卡顿的三类根因：

1. **主线程长任务**：大数据处理、大列表渲染、同步计算——切分任务/虚拟列表/搬 Web Worker；
2. **回流风暴**：几何属性在循环里改——批量读、用 transform；
3. **分层爆炸/透明窗口成本**：Electron 里透明窗口（本项目浮窗）渲染成本显著高于普通窗口——内容克制、动画只走合成层。

**特殊认知**：**Electron 的卡顿可能根本不在渲染进程**——主进程被阻塞时所有窗口的 IPC 都延迟（转写结果推不过去、invoke 不返回），表现就是"界面卡死"。所以"卡顿"先确认卡在哪个进程：是页面掉帧（渲染进程），还是 IPC 无响应（主进程）。

### Q50. 进程崩溃怎么定位？（讲你的真实案例）

**考什么**：JD 第 5 条"进程崩溃"，最爱听真实 debug 故事。

**答案**（结合本项目两个真实案例）：

**案例一：TSFN 退出竞态**。现象：退出应用偶发崩溃，崩溃栈指向原生模块释放。分析：采集线程在 GetNextPacketSize 上阻塞（loopback 无渲染流就不产生包），主线程直接释放 ThreadSafeFunction——释放与活跃线程竞态。定位方法：崩溃转储 + 线程栈对照（释放发生在采集线程仍存活时）。修复：先 Stop 唤醒 → join 等线程退出 → 再释放（Q37 的退出顺序）。**经验：原生模块的资源生命周期必须与线程生命周期配对**。

**案例二：webContents.send 崩溃**。现象：窗口关闭瞬间主进程抛异常崩溃。分析：send 的目标窗口已销毁，webContents 变成无效句柄，Electron 抛 "Object has been destroyed"。修复：统一封装 send，发送前判 isDestroyed。**经验：跨进程句柄都是"可失效的"，主进程持有窗口引用必须防御性判活**。

**通用排查框架**（被问"GPU/随机崩溃"时）：渲染进程崩溃开 webContents 的 render-process-gone 拿 crashReason → 可疑 GPU 问题先用 app.disableHardwareAcceleration() 二分排除 → 崩溃转储 + 最小复现 + 版本回退二分。

### Q51. 包体积怎么优化？

**考什么**：JD 第 4 条打包延伸。

**答案**：Electron 体积组成 = 运行时（Chromium+Node，约 80MB 底座，减不动）+ 应用代码 + 依赖。

- **files 白名单**：electron-builder 只打包声明目录——node_modules 里 devDependencies、测试、文档全部排除（Vite 产物 + 主进程 tsc 产物 + 原生 .node）；
- **依赖瘦身**：主进程依赖能省则省（ws、eventemitter3 这种小而精的）；渲染层依赖经 tree-shaking；
- **asar 打包**：应用代码打成 asar 归档（读取快、防篡改），需要被外部进程读取的文件（原生 .node）配置 unpacked；
- **双架构**：Windows x64/arm64、macOS universal——按目标用户出包，别一个包塞所有架构；
- **分发包 vs 应用**：Squirrel/NSIS 安装器支持差分更新，用户日常下载的是差分包不是全量。

**结合本项目**：主进程依赖刻意精简（ws + eventemitter3，重逻辑自研）；原生插件按平台条件编译（binding.gyp 的 OS 条件只链 Windows 库）。

### Q54. 怎么组织上下文、拆任务、写提示词？

**考什么**：JD 硬性第 3 条"上下文组织、任务拆解和提示词表达"。

**答案**：

**任务拆解**：大需求拆到**可验证的中间产物**——不是"帮我写个音频模块"，而是"先写采集接口定义和错误分类 → 再实现 WASAPI 路径 → 再写归一化单测"。每步有明确验收标准（编译过、测试过、可运行）。**拆解的粒度 = 验证的粒度**。

**上下文组织**：给 AI 的不是"整个项目"，而是**任务相关的最小上下文**：相关文件内容、类型定义、错误日志、约束清单。关键技巧是**约束先行**——"已有内容不要改""遵循现有命名规范""修改必须通过 typecheck + vitest"，把验收标准写在任务里，而不是事后补救。

**提示词结构**：角色 + 背景（项目/现状）+ 目标（明确交付物）+ 约束（技术栈、规范、禁区）+ 验收标准（怎么算完成）+ 示例（有参照给参照）。**提示词写得好不好，看它像不像一份需求文档**——这也是 AI 时代对工程师"需求表达"能力的强化要求。

### Q55. 你怎么审查、验证、修正 AI 生成的代码？

**考什么**：JD 硬性第 3 条"审查、验证和修正"。

**答案**：四道闸：

1. **编译/类型闸**：typecheck（本项目双 tsconfig）不过的直接打回——AI 代码常见的类型错误、未用导入第一道就拦住；
2. **测试闸**：单测是 AI 代码的"验收单"（本项目 vitest 跑协议编解码、归一化的字节级对齐用例）——AI 改完必须全绿，测试本身就是规格；
3. **人工 review 闸**：像审同事代码一样审 AI 代码——接口设计是否合理、错误路径是否覆盖、有没有顺手引入依赖、注释与实现是否一致。**AI 的注释有时比代码更自信**，注释和代码矛盾时以代码为准再去验证；
4. **事实核验闸**：AI 提的"事实性建议"必须独立查证——比如它建议某库某 API 的用法，我会对照官方文档确认。本项目里 Electron ABI 重编译、WASAPI 调用顺序这类细节，都对照了官方文档/实测验证过。

**修正的案例**：AI 第一版方案往往"能跑但不最优"——比如镜像下载最初建议单源重试，实测后改成 7 镜像轮换 × 每源退避 × 全局兜底。**修正 AI 的不是代码格式，是方案判断**——这正是资深工程师的价值所在。

### Q56. AI 辅助开发的安全与质量边界？

**考什么**：JD 硬性第 4 条"安全和质量边界，不盲目采用"。

**答案**：

1. **数据边界**：密钥、用户数据、公司内部代码不进外部 AI 服务——本地化工具优先，敏感信息脱敏后再问；本项目音频内容、用户文件路径这类隐私数据从不发给 AI 调试；
2. **依赖边界**：AI 建议引入的新依赖一律人工审查（维护状态、下载量、协议、源码体积），供应链投毒是 AI 辅助开发时代风险最高的环节——本项目恰好靠 contextBridge 白名单把依赖风险隔离在渲染层，但依赖审查本身不可省；

4. **信任边界**：AI 的"自信"与"正确"无关。凡涉及安全、并发、原生资源、协议兼容的代码，一律人工验证（文档核对 + 压测 + 字节级测试）。**AI 提效率，人把正确性**——这条线不能松。

## 八、技术负责人能力（JD 第 5/7 条）

### Q59. 一个复杂需求你怎么拆？（模块设计）

**考什么**：JD"复杂业务拆解能力"。

**答案**（结合本项目音频管线）：拿到"桌面端实时翻译"这个需求，先问边界（哪端采集、什么协议、容错要求），再按**数据流向**拆层——每层一个输入、一个输出、一个职责：

```
WASAPI 采集(原生) → 归一化(格式统一) → 帧累积(流→帧) → 协议编码(帧→字节) → WebSocket(传输) → 重连/会话(可靠性)
```

拆解标准：**每层可独立测试**（归一化有字节级单测、协议有三端对齐测试）、**每层可替换**（归一化算法升级不影响传输）、**每层有明确错误边界**（E_WASAPI/E_PCM 错误分类）。拆得对的特征：别人接手任何一层，不需要理解其他层的实现。

### Q60. 接口抽象怎么做？（讲一个具体设计）

**考什么**：JD"接口抽象能力"。

**答案**（结合本项目三个抽象实例）：

1. **采集接口平台无关**：audio-capture 对上层只暴露 start(source)/stop() + EventEmitter 事件——Windows 下是 WASAPI 插件，将来 macOS 换成别的实现（getDisplayMedia/ScreenCaptureKit 或 CoreAudio），**上层业务代码零改动**。接口面向能力定义，不面向平台定义；
2. **preload 即 SDK**：渲染进程拿到的 window.electronAPI 是四分类白名单（含类型声明）——渲染层不知道"主进程怎么实现"，只知道"能做什么"。**进程边界 = 接口边界**，两层可独立演进；
3. **协议即契约**：Wire Protocol 三端各写各的编解码（TS DataView / Kotlin ByteBuffer / Python struct），靠**同一套字节级测试**保证一致——接口文档会过期，测试不会。

抽象原则一句话：**定义接口时想"如果实现要换，哪里会疼"，把疼点隔离在接口后面**。

### Q61. 怎么安全地重构？

**考什么**：JD"代码重构能力"。

**答案**（结合本项目 interview-reducer 案例）：重构三步：

1. **先找纯逻辑**：把状态机逻辑从 React Native 组件/hook 里抽成纯函数（无副作用、无 UI 依赖）——这是最小风险的一步，因为可以**原样搬移**再补测试；
2. **测试保护**：给抽出的纯逻辑补全单测（每个 action → 期望状态），此后每一步重构都有回归网兜底；
3. **接口冻结 + 渐进替换**：迁移期间新旧共存，切换开关逐步放量，确认等价后删旧。

**判断重构是否该做的标准**：当前结构是否阻碍了明确的需求（本项目的明确需求：RN/Electron/Web 三端复用同一状态机）。**为重构而重构不做，为复用而重构才做**。

### Q62. 技术决策的 trade-off 怎么表达？

**考什么**：JD"技术判断力"，面试官靠这个区分"执行者"和"决策者"。

**答案**：表达框架——**约束 → 候选 → 权衡 → 结论**，四段讲完一个决策。结合本项目三个真实决策：

1. **WASAPI 轮询 vs 事件驱动**：约束是"代码简单可控 + 10ms/40ms 量级精度要求"→ 事件驱动省 CPU 但线程同步复杂，轮询最多延迟 10ms 不影响 40ms 帧周期 → 选轮询。**"够用且简单"是合法的工程决策**，不是所有场景都要最优解；
2. **JSON vs 二进制协议**：约束是"每秒 25 帧持续上行 + 三端实现成本"→ JSON 省开发成本但膨胀 33%+解析开销，二进制省 40% 带宽、固定偏移解码 → 选二进制，因为这是**每秒发生 25 次的成本**，一次性开发成本摊薄到零；
3. **本地转换 vs 后端 API**：约束是"离线可用 + 隐私"→ 后端方案效果最好但违背核心约束 → 选 LibreOffice 本地。

**表达要点**：不吹自己的方案是最优解，说清"在什么约束下这个选择成立"——决策的合理性来自约束的合理性。

### Q63. 跨端/跨团队协作怎么保证质量？

**考什么**：JD"沟通协作能力"。

**答案**（结合本项目双端一后端协作）：协作的三个抓手：

1. **契约先行**：协议字段、帧格式、错误码在动手前定稿并写进测试——本项目的 Wire Protocol 三端字节级测试让"我以为你按这个来"变成"测试说我们一致"；
2. **算法等价验证**：归一化算法两端各自实现（TS/Kotlin），用同一组输入断言字节级输出一致——**浮点运算的精度都对齐**，后端收到的帧无法区分来源，双端体验一致；
3. **错误分类共享**：错误码（E_WASAPI/E_PCM、可恢复/不可恢复）是三端共同的"语言"——排查线上问题时任何一端报错码，其他端秒懂。

协作的本质：**把口头约定变成机器可验证的约定**——人之间的误会减少多少，取决于多少约定不需要人解释。

| 为什么 contextBridge | 渲染进程视为不可信，nodeIntegration 开着 XSS 就变 RCE；默认安全开关 + 白名单 |
| IPC 两种模式 | invoke/handle 一问一答，send/on 单向推送；载荷结构化克隆，高频大块用 MessagePorts |
| 原生模块链路 | node-gyp 编译，N-API 稳定 ABI，node-addon-api 是 C++ 封装，TSFN 解决跨线程调 JS |
| 重连设计 | 关闭码判断 → 指数退避防雪崩 → generation 防竞态 → session 恢复无感 |
| 内存泄漏排查 | app.getAppMetrics 分进程 → 堆快照对比 → 三大源：IPC 监听器、窗口引用、全局引用 |
| 崩溃排查 | 崩溃栈 + 线程栈对照；原生资源生命周期与线程配对；send 前判活 |
| Vite 为什么快 | 开发期原生 ESM 按需编译 + esbuild 预构建 + HMR 精确失效 |
| pnpm 原理 | 全局 store 硬链接 + 非扁平结构，幽灵依赖直接报错 |
| Fiber 解决什么 | 递归同步 diff → 可中断链表遍历 + 优先级调度，长任务不再卡帧 |
| 事件循环 | 宏任务一个 → 微任务清空 → 渲染时机；主进程和渲染进程各一条循环 |
| HTTP 三代 | 1.1 串行开 6 连接；2 多路复用但 TCP 队头阻塞；3 QUIC/UDP 无队头阻塞 |
| AI 工具分工 | IDE 内短交互，CLI Agent 长任务，对话式调研；验证闭环人负责 |
| AI 边界 | 数据不进外部服务、依赖人工审查、AI 代码与手写同标准、事实性建议查证 |
