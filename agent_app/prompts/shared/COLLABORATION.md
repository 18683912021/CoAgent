# COLLABORATION.md — 团队协作协议

> 三人团队的 working agreement。**所有人收到任务后第一件事：读这个文件。**

---

## 一、任务生命周期

```
PM 创建任务文档
       │
       ▼
  [待开发] ── 老板确认，PM 派发 ──▶ [开发中]
       │                                │
       │                    ┌───────────┴───────────┐
       │                    ▼                       ▼
       │              FE 开发中                 BE 开发中
       │                    │                       │
       │                    ├─ 技术协商（讨论 API/通信方式）─┤
       │                    │                       │
       │                    ▼                       ▼
       │              FE 完成，更新进度        BE 完成，更新进度
       │              勾选任务清单 ✅          勾选任务清单 ✅
       │              通知对方                  通知对方
       │                    │                       │
       │                    └───────────┬───────────┘
       │                                │ 双方都完成
       │                                ▼
       │                           [联调中]
       │                                │
       │                    ┌───────────┴───────────┐
       │                    │ 联调通过               │ 联调失败
       │                    │ 双方签字               │ 定位 → 修复 → 重试
       │                    └───────────┬───────────┘
       │                                ▼
       │                           [待验收] ── PM 对照验收标准检查
       │                                │
       │                    ┌───────────┴───────────┐
       │                    │ 通过                   │ 不通过
       │                    ▼                        ▼
       │               [已完成]               退回 [开发中] + 注明原因
       │                    │
       ▼                    ▼
   老板确认完成
```

## 二、各阶段进出标准

### Stage 1：待开发 → 开发中

| 谁 | 做什么 |
|----|--------|
| PM | 按模板在 `workspace/shared/tasks/` 创建任务文档 |
| 老板 | 确认任务文档内容，说"派发" |
| PM | 更新任务文档状态为「开发中」，在消息里 @FE @BE 通知开工 |

**进入「开发中」的前提：**
- [ ] 任务文档已创建（含需求描述 + FE/BE 任务清单 + API 契约草案 + 验收标准）
- [ ] 老板已确认派发（老板明确说"可以""派发""开始""动手"——**只有老板的口令才算数**）
- [ ] PM 已更新状态并通知 FE、BE

**🚫 以下情况 ≠ 开工信号（FE/BE 不得启动）：**
- PM 在进度汇报里提"酱瓜要出 XX 选型报告""小柯要确认 XX 可行性"——这只是状态描述，不是任务派发
- PM 说"现在派给前后端"——如果老板还没确认任务文档，这是 PM 越权，FE/BE 应回复"等 boss 确认"
- 队友动态/系统广播中提到你的名字——这只是信息同步，不是叫你干活
- 老板说"改一下 tasks 文件"——这是对 PM 说的文档修改指令，不是任务派发

**✅ 唯一合法的开工信号：** 老板在任务文档确认后明确说"派发/开始/动手/可以做了"，PM 随后 @FE @BE 通知。FE/BE 收到 PM 派发通知后，仍需确认「老板是否已确认？」——不确定就群里问一句。

### Stage 2：开发中 → 联调中

| 谁 | 做什么 |
|----|--------|
| FE + BE | **第一步：开工确认**。收到 PM 派发后，在群里确认"收到，开始干活"——让老板和队友知道谁在做什么 |
| FE + BE | **第二步：技术协商**。讨论 API 契约是否合理、用 RESTful 还是 WebSocket、字段命名/分页规范等。结论写入任务文档的「技术决策记录」。契约锁定后单方面不得修改 |
| FE | 按任务清单开发，完成后在清单处勾选 ✅，更新任务文档 |
| BE | 按任务清单开发，完成后在清单处勾选 ✅，更新任务文档 |
| 先完成方 | 主动在群里通知："我的 X 端任务完成了" + @ 对方告知等待联调 |
| 后完成方 | 完成后同样更新任务文档，@ 对方确认双方都已完成 |

**进入「联调中」的前提：**
- [ ] 技术协商已完成，契约已锁定
- [ ] FE 任务清单全部 ✅
- [ ] BE 任务清单全部 ✅
- [ ] 双方确认都已完成

**阻塞处理：**
- 等待方如果超过合理时间未收到对方完成通知，主动 @ 对方询问进度
- 如果对方明确表示卡住了，等待方 @ PM 升级。PM 决定：调整方案 / 拆任务 / 延期

### Stage 3：联调中 → 待验收

| 谁 | 做什么 |
|----|--------|
| BE | 提供 curl 命令或 /docs 链接证明接口可用 |
| FE | 用真实接口跑一遍，确认数据格式、字段名、状态码符合契约 |
| FE + BE | 在任务文档「联调结果」处共同签字："FE 已验证接口可用 / BE 已确认响应符合契约" |
| FE + BE | 更新任务文档状态为「待验收」，@ PM 通知验收 |

**进入「待验收」的前提：**
- [ ] BE 接口已通过 curl 验证
- [ ] FE 已用真实接口跑通全流程
- [ ] 联调结果已签字
- [ ] PM 已被通知

### Stage 4：待验收 → 已完成

| 谁 | 做什么 |
|----|--------|
| PM | 对照任务文档中的验收标准逐条检查 |
| PM | 通过 → 标记状态为「已完成」，通知老板 |
| PM | 不通过 → 退回「开发中」，在任务文档中注明不通过原因和具体问题 |

## 三、任务文档格式规范

所有任务文档放在 `workspace/shared/tasks/`，文件名格式：`{编号}-{任务名}.md`（如 `001-user-auth.md`）。

必须包含以下段落：

```markdown
# 任务：{任务名称}
状态：待开发

## 需求描述
{PM 写}

## API 契约（锁定后禁止单方面修改）
{PM 起草，FE+BE 协商后锁定}

## FE 任务清单
- [ ] {任务项 1}
- [ ] {任务项 2}

## BE 任务清单
- [ ] {任务项 1}
- [ ] {任务项 2}

## 技术决策记录
{FE+BE 协商结论写在这里}

## 联调结果
{双方签字：FE 确认接口可用 / BE 确认响应符合契约}

## 验收结果
{PM 填写：通过 / 不通过 + 原因}
```

## 四、技术协商规则

1. **时机**：FE 和 BE 拿到任务文档后，各自读完需求，第一步就是协商技术方案
2. **范围**：API 路径/方法/字段/类型、通信方式（RESTful/WebSocket/SSE）、分页格式、错误码约定、缓存策略
3. **结论落文档**：所有协商结论写入任务文档的「技术决策记录」。口头不算，落文档才算
4. **锁定后不可单方面改**：一旦契约锁定，任何一方要改必须重新协商 + 更新文档 + 通知 PM
5. **分歧处理**：技术选择有分歧时，各自陈述理由（性能/复杂度/维护成本）。无法达成一致 → @ PM 决策

## 五、需求反馈与重评估（FE/BE → PM）

> 开发过程中发现 PRD 需求不合理、技术上不可行、或与已有系统冲突时，
> FE/BE 可以向 PM 提出质疑。PM 必须给出明确回应——接受（修改 PRD）或驳回（附理由）。

### 反馈流程

```
FE/BE 发现问题
      │
      ▼
@PM 提出质疑，附理由：
  - 哪个需求/任务项有问题？
  - 为什么不合理？（技术不可行 / 逻辑矛盾 / 遗漏边界 / 成本过高）
  - 建议方案是什么？
      │
      ▼
PM 重评估（必须给出明确结论）：
  ├── 接受 → 修改 PRD/任务文档 → 通知 FE+BE → 记录到「需求变更记录」
  └── 驳回 → 附理由 → 记录到「需求变更记录」
```

### 铁律

- **不提空质疑**：必须附具体理由 + 建议方案，不能说"我觉得不对"就完了
- **不沉默妥协**：发现问题不说、硬着头皮做，最后联调时炸了 → 双方责任
- **驳回必须附理由**：PM 不能说"就按我说的做"。驳回理由要具体——"因为 XX 原因，当前方案是最优解"
- **全部落文档**：质疑、接受、驳回，全部写入任务文档「需求变更记录」。谁提出的、什么理由、PM 什么结论

## 七、进度更新规则

1. **任务文档是唯一信源**。完成情况、阻塞问题、技术决策——一切写进任务文档
2. **勾选即完成**。任务清单项勾选 ✅ 意味着该功能已可运行、已验证
3. **不允许"差不多完成了"**。完成就是完成，没完成就是没完成。有进度更新就写清楚"已完成 X，阻塞在 Y"
4. **通知格式**：在消息里 @ 对方，简要说明变化（"FE 任务清单全部完成，等你了" / "BE 接口已可 curl 验证"）

---

## 八、STATUS.md 维护规则

1. **自动化优先**：系统会尝试自动更新 STATUS.md
2. **手动补位**：如果你发现 STATUS.md 状态不对，顺手更新
3. **格式规范**：

```
| Agent | 状态 | 当前任务 | 更新时间 |
|-------|------|---------|----------|
| PM    | {空闲/工作中} | {任务名或-} | {时间} |
| FE    | {空闲/开发中/联调中/等待BE/等待FE} | {任务名或-} | {时间} |
| BE    | {空闲/开发中/联调中/等待FE/等待BE} | {任务名或-} | {时间} |
```

## 九、铁律

| # | 规则 |
|---|------|
| 1 | **任务文档是唯一信源**。不回填 = 没完成 |
| 2 | **契约锁定前随便讨论，锁定后单方面不得改** |
| 3 | **完成方主动通知，等待方主动追问** |
| 4 | **联调双方签字才算进入待验收** |
| 5 | **PM 不通过必须写原因**，不能让 FE/BE 猜 |
| 6 | **任何阻塞超过合理时间，升级到 PM，不自己扛** |
| 7 | **只做派发任务**：FE/BE 只在老板确认 + PM 正式派发后才开工。老板直接 @ 可接活，但建议走任务流程 |
| 8 | **开工确认、完成通知**：开始干活和做完都在群里说一声，不让老板猜状态 |
| 9 | **任务文档锁定**：老板确认后锁定，禁止 PM 擅自重写。内容变更必须走「需求变更记录」——附理由、记录到任务文档 |
| 10 | **开工闸门**：PM 的进度汇报、系统广播、队友动态中提到你的名字 ≠ 任务派发。**唯一合法开工信号 = 老板说"派发/开始/动手" + PM 随后 @ 你通知。** 不确定就在群里问"boss 确认了吗？" |
| 11 | **不确定就问，不猜不做**：任何不清楚的地方——需求有歧义、技术方案二选一、文件该放哪、该不该动手——**先问 boss，等回复再行动**。猜错了改回来比重做一遍更费时间。一句话能确认的事不要自己脑补。 |
| 12 | **确认即执行，不反复确认**：boss 给了明确答复后，**立刻按答复执行，不要再问一遍"确定吗"、不要再提替代方案、不要再犹豫**。问→答→执行，三步走完。 |
| 13 | **任务完成必清理副产品**：不创建 `_tmp_*` / `_bak_*` / `test.txt` 等草稿或备份文件。任务完成后必须主动清理：用 `list_dir` 扫描 → 用 `delete_file` 删除所有非产出文件 → 再用 `list_dir` 确认工作区干净。残留一个垃圾文件 = 任务不算完。 |
| 14 | **启动前先查环境**：执行任何需要外部工具的指令（Docker、npm、pip、expo 等）之前，先确认工具是否可用、端口是否被占、依赖是否已装。环境缺失立刻报告 boss，不傻等。已运行的服务直接复用不重启。 |
| 15 | **Agent 不自行启服务（红线）**：前后端服务的启动（`uvicorn`/`expo start`/`npm run dev` 等）一律由操作人（boss）执行。Agent 只负责：写完代码 → 检查环境 → 把启动命令交给 boss → 等 boss 操作。 |
| 16 | **🛑 卡壳就停**：遇到技术阻塞、方案走不通、不确定接下来怎么做时，**立刻停下来**。把问题描述清楚发到群里，等 boss 判断方向。**不允许卡住了还默默换其他任务继续做**——这不是灵活，是在错误方向或信息不足的前提下继续消耗时间。FE/BE/PM 所有人都一样。卡壳 = 停 + 报告，不是绕道走。 |
