## 需求分析方法论

### 用户故事标准模板
```
作为 {角色}

验收条件：
- [ ] {条件1}
- [ ] {条件2}
```

### 场景覆盖清单
每个功能必须覆盖四种场景：
| 场景 | 示例 |
|------|------|
| 正常流程 | 用户输入正确信息，操作成功 |
| 边界条件 | 输入最大值、空列表、超长文本 |
| 异常情况 | 网络错误、权限不足、数据冲突 |
| 空状态 | 首次使用、数据为空、搜索无结果 |

### 5Why 根因分析
```
用户说："我想要一个导出按钮"
  Why? → "我要把数据给老板看"
  Why? → "老板每周要看销售报表"
  Why? → "老板用报表做决策"
  → 真正需求：自动生成周报并推送给老板，而非手动导出
```

## 优先级排序方法

### RICE 模型
```
Score = (Reach × Impact × Confidence) ÷ Effort

Reach: 影响多少用户？（人数/比例，1-10）
Impact: 对用户的价值多大？（1-10）
Confidence: 有多确定？（100%=1.0, 80%=0.8, 50%=0.5）
Effort: 开发成本？（人天，1-10）

示例：
功能A: (8 × 9 × 0.8) ÷ 5 = 11.52
功能B: (5 × 7 × 0.9) ÷ 3 = 10.50
→ 功能A 优先
```

### MoSCoW 备选（干系人沟通用）
- Must have: 缺了不可用（P0）
- Should have: 应该要有（P1）
- Could have: 可以有（P2）
- Won't have: 明确不做（本版本排除）

## 追问技巧

| 用户说 | PM 追问 | 目的 |
|--------|--------|------|
| "做个简单的功能" | "你说的简单，具体指几步操作？" | 消除模糊 |
| "随便设计" | 给推荐方案+理由，不等确认 | 主动引导 |
| "和XX产品一样就行" | "XX产品的哪个版本？哪些功能是你需要的？" | 精准对标 |
| "我觉得应该加个按钮" | "这个按钮解决什么问题？有用户反馈吗？" | 挖掘根因 |
| "尽快上线" | "最早可接受的时间是？哪些功能可以先不做？" | MVP 裁剪 |
| "老板说要..." | "老板的核心目标是什么？有可量化的 KPI 吗？" | 向上对齐 |
| X 和 Y 矛盾 | "这两个需求有冲突——X 要求实时，Y 要求离线。你倾向哪个？" | 暴露冲突 |

## 不同产品类型的设计要点

### SaaS 管理后台
- 仪表盘：核心指标卡片 + 趋势图 + 快捷操作
- RBAC：角色（超级管理员/管理员/普通成员）× 权限（读/写/删）
- 操作日志：谁 + 什么时间 + 做了什么 + IP
- 数据导出：CSV/Excel，支持筛选后导出
- 批量操作：全选、批量删除、批量导出

### C 端移动应用
- 新手引导：3 步内让用户感受到核心价值
- 推送策略：场景化推送（非骚扰），支持免打扰时段
- 社交裂变：邀请码、分享海报、拼团
- 性能：首屏加载 < 2s，接口响应 < 500ms

### 小程序
- 审核合规：内容审核规范、隐私协议
- 获客：搜索优化、附近小程序、二维码
- 裂变：分享卡片设计、群聊分享、朋友圈
- 限制：包体积 2M、分包 20M、支付需微信认证

### AI 产品
- Prompt 设计：系统提示词、温度参数、Token 控制
- 知识库：RAG 检索流程、文档切分策略、向量化
- 交互设计：流式输出、加载状态、重试机制
- 安全：内容审核、敏感词过滤、用户隐私
- 成本：Token 消耗计算、免费额度/付费策略

## PRD 质量规范

> 好的 PRD：FE 和 BE 看完不用追问就能开工。坏的 PRD：开发过程中反复 @ 你确认。

### 常见 PRD 缺陷与修复

| 缺陷 | 坏示例 | 好示例 |
|------|--------|--------|
| **模糊措辞** | "列表性能要好" | "首屏加载 ≤ 1s，滚动 1000 条无明显卡顿" |
| **缺失边界** | "用户可以删除数据" | "删除需二次确认；已删除数据 30 天内可恢复；批量删除上限 100 条" |
| **不完整的契约** | `GET /api/users` | `GET /api/users?page=1&limit=20&search=&role=` → `{items: [...], total: 42}` |
| **假验收标准** | "功能正常可用" | "输入 11 位手机号 + 6 位验证码 → 点击登录 → 跳转首页并显示用户名" |
| **技术越界** | "用 Redis 缓存用户数据" | "用户数据需缓存（方案由 BE 决定），过期时间建议 30 分钟" |
| **优先级通胀** | 12 个 P0，6 个 P1，3 个 P2 | P0 ≤ 3 个（缺了产品不可用），P1 4-6 个，其余 P2 |
| **遗漏空状态** | 列表页只画了有数据的样子 | "无数据时展示空状态插图 + '暂无记录，去创建第一个吧' + 创建按钮" |
| **用户流程太粗** | "用户登录后进入首页" | "输入手机号 → 获取验证码(60s 冷却) → 输入验证码 → 首次登录补全昵称+头像 → 进入首页" |

### 验收标准「可验证」铁律

每条验收标准必须包含：**操作 + 预期结果**，让测试的人不看 PRD 正文也能执行。

```
❌ "搜索功能正常"                           ← 怎么算正常？
✅ "输入'张三'点击搜索 → 列表只显示含'张三'的条目 → 清空搜索框 → 列表恢复全部数据"
❌ "权限控制正确"                           ← 哪个角色的什么权限？
✅ "管理员登录 → 可见'删除'按钮 → 普通用户登录 → 不可见'删除'按钮"
❌ "移动端适配完成"                         ← 怎么验证？
✅ "iPhone 14 (390×844) / 小米 14 (393×873) → 页面无横向滚动条，按钮可点击不重叠"
```

### 调研质量标准

搜索 ≠ 调研完成。好的调研满足三条：

1. **来源可信**：优先官方文档/官网 > 知名科技媒体 > 个人博客。标注来源 URL
2. **时效性**：优先 1 年内信息。如果只搜到 2 年前的结果，标注「信息可能过时」
3. **交叉验证**：同一结论至少 2 个独立来源确认。只有 1 个来源 → 标注「单一来源，待验证」

```
❌ 只搜 1 次 + 只看摘要 → "XX 产品支持实时协作"
✅ 搜 3 次不同角度 → web_fetch 打开 3 个链接读全文 → 结论："官方文档+2 篇评测均确认支持实时协作"
   来源：docs.xx.com/features | techcrunch.com/xx-review | zhihu.com/xx-vs-yy
```

## 任务拆解规范

> 拆太粗 → FE/BE 不知道从哪下手。拆太细 → 文档比代码还长。

### 粒度标准

| 角色 | 拆解粒度 | 好的任务描述 | 坏的任务描述 |
|------|---------|-------------|-------------|
| FE | 1 个组件 ≈ 1 条任务 | `UserTable 组件 — 列表展示+搜索+排序+分页 — 验收：四种状态` | `做用户管理页面` |
| FE | 1 个复杂交互 ≈ 1 条任务 | `登录表单 — 手机号验证码登录+60s 倒计时+错误提示 — 验收：正常/手机号格式错误/验证码错误/网络超时` | `做登录` |
| BE | 1 个接口 ≈ 1 条任务 | `GET /api/users — 列表查询+分页+搜索+角色过滤 — 验收：curl 返回 items+total` | `做用户接口` |
| BE | 1 个数据模型 ≈ 1 条任务 | `User 模型 — id/uuid/username/email/role/is_active/时间戳 — 验收：alembic upgrade 建表成功` | `建用户表` |

### 验收标准对齐检查

FE 和 BE 的验收标准要能"对上"——前端验收的点，后端能提供接口支撑。

```
✅ 对齐的：
  FE: "用户列表加载 → 骨架屏 → 数据显示 → 每页 20 条"
  BE: "GET /api/users?page=&limit= → {items(≤20), total, page, limit}"

❌ 未对齐的：
  FE: "用户列表支持拖拽排序"
  BE: 没有对应排序接口 ← 漏了
```

### 依赖声明

如果任务之间有依赖，必须在任务清单中显式标注：

```markdown
## FE 任务清单
- [ ] 0. 环境搭建 — 复制 rn-app-shell → 安装依赖 → 跑通 Expo
- [ ] 1. 登录页面（依赖：BE 任务 1「POST /api/auth/login」就绪后联调）
- [ ] 2. 首页（无依赖，可独立开发）

## BE 任务清单
- [ ] 0. 项目初始化 — FastAPI + SQLAlchemy + Alembic
- [ ] 1. POST /api/auth/login（FE 任务 1 依赖此接口）
- [ ] 2. User 模型 + 迁移脚本（无依赖）
```

### 常见拆解错误

| 错误 | 说明 | 修复 |
|------|------|------|
| **隐含子任务** | "实现用户管理"包含列表/详情/创建/编辑/删除 5 个功能 | 拆成 5 条独立任务 |
| **伪独立** | FE 任务 3 "展示订单详情"依赖 BE 任务 5 的接口，但文档没写 | 标注依赖 |
| **技术任务混入** | FE 清单里有 "配置 Webpack"，这是技术决策不是产品任务 | 删掉——技术选型留给 FE/BE |
| **验收标准当任务** | 把验收条件写成任务（"确保页面不卡顿"） | 验收标准放验收列，不放任务列 |
